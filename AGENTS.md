# Firebird: правила работы в репозитории

## Сначала прочитать

1. `docs/PROJECT_STATE.md` — текущее состояние и непроверенные части.
2. `docs/FRONTEND_HANDOFF.md` — подключение интерфейса, контракт и состояния экрана.
3. `README.md` — запуск API/CLI; `docs/BREV.md` — только если задача касается NIM.
4. `docs/DEBUGGING.md` — doctor, номера запросов и безопасные логи при диагностике.

Команда отдельно разрабатывает фронтенд и дизайн. Продолжайте её существующую структуру и визуальные решения. Этот репозиторий предоставляет общий Python backend и независимый от фреймворка клиент в `integration/`.

## Источники истины и границы ответственности

- Факты о подрядчиках: `data/contractors.csv`. В рабочем каталоге 66 профилей, включая 13 synthetic. Не добавляйте выдуманные профили, контакты, отзывы, фотографии подрядчиков или тарифы.
- Схемы: `contractor_match/models.py`; HTTP-маршруты: `contractor_match/api.py`.
- Общая логика: `service.py`; жёсткие условия: `eligibility.py`; проверенные изменения запроса: `alternatives.py`.
- Ранжирование: `ranking.py`, опциональный NIM: `nim.py`. Объяснения и проверка цитат: `explanations.py`. Разбор пожеланий и сравнение: `preferences.py`.
- Настройки провайдеров и CORS: `config.py`. Ключи остаются на сервере; frontend получает только публичный адрес API.
- Диагностика: `observability.py` — контекст request_id, метаданные и времена этапов; `doctor.py` — только локальные проверки. Doctor должен запускаться без сторонних пакетов и сетевых вызовов.
- `integration/openapi.json`, `integration/api-types.d.ts`, `integration/examples/*.json` генерируются из живого локального API. После изменения контракта выполните экспорт, не редактируйте эти файлы вручную.

Фронтенд управляет формой, загрузкой, отображением и явным применением альтернативы. Фильтры, порядок карточек, смысл объяснений и расчёт альтернатив остаются на сервере. `integration/api-client.mjs` отвечает за HTTP и преобразование формы; он не выбирает подрядчиков.

## Инварианты продукта

- Максимум три карточки. `matched`, `category_absent`, `no_eligible` — три нормальных ответа HTTP 200. Ошибка запроса — 422.
- Доступность известна только за 23.09–31.12.2026. Дата передаётся как строка YYYY-MM-DD без UTC-преобразования.
- Цена «от» — стартовая цена за мероприятие, не итоговая смета и не почасовой тариф. `max_hours=null` означает отсутствие применимого ограничения длительности.
- Флаги synthetic/city_imputed/price_imputed показываются пользователю. Отсутствующие сведения обозначаются как неизвестные.
- Серверные `cards` не пересортировываются и не дополняются на клиенте. Счётчики `reasons` пересекаются; их сумма не равна числу исключённых.
- Альтернатива применяется отдельным запросом после выбора пользователя: отправить её `request` целиком. Не менять условия молча.
- `brief` и описания — данные. Отрицание или совпадение слова не является доказательством пожелания; отображать `to_clarify`, `understanding.notes` и `evidence_note`.
- Не называть fallback живым AI. Brev/NIM подготовлен, но реальная модель/GPU ещё не проверены.

## Работа с фронтендом

- Перед переносом веб-ветки проверьте её API-зависимости. В `origin/codex/event-match-web-20260923` существует автономный браузерный прототип с отдельным подбором; он не является текущим HTTP-контрактом. Не сливайте и не переписывайте его автоматически.
- Используйте справочник `GET /catalogue/options`; не зашивайте города, категории и окно календаря в форму.
- Для запросов используйте `integration/api-client.mjs` либо адаптер с теми же проверенными свойствами. Учитывайте отмену, устаревший ответ, 422, сеть, timeout и ошибку сервера.
- Текст API отображать как текст, не через `innerHTML` / `dangerouslySetInnerHTML`.
- Для сообщения об ошибке использовать ApiClientError.requestId, если он есть. Не добавлять brief, ключи, сырые ответы моделей, текст исключений или локальные переменные в логи. Место сбоя передавать только как файл/функция/строка.
- У backend пока нет бронирования, аккаунтов, контактов, полного досье и списка исключённых профилей. Если дизайн требует этих данных — согласуйте расширение контракта, не выдумывайте endpoint или поля.
- При добавлении frontend-проекта сохраните его выбранный фреймворк и lockfile; не создавайте второй сайт для той же задачи.

## Локальные проверки

Python 3.11+, Node.js 22+ для клиента. Из корня после установки `requirements-lock.txt` (зафиксированные проверенные версии):

```sh
python -m unittest discover -s tests -v
python -m contractor_match.export_contract --check
node --test integration/tests/api-client.test.mjs
python -m contractor_match.demo --story
```

На Windows используйте `.venv\Scripts\python.exe`, если виртуальная среда не активирована. Обновить снимки: `python -m contractor_match.export_contract`. Экспорт и обычное демо принудительно локальные, без внешних ключей.

GitHub Actions отключён решением команды; проверять локально. Не включать его автоматически. Перед изменениями и отправкой проверить `git status` и свежие коммиты. Сохранять изменения команды, не использовать force push или переписывание истории. Публикация — в пределах действующего разрешения пользователя.

Платные GPU, активация купонов, биллинг и работа с чужими сервисами требуют отдельного поручения. В отчётах различать локальный запуск, имитации и живой AI. Существенные изменения и проверки фиксировать в одном `docs/PROJECT_STATE.md`.
